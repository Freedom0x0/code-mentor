# code-mentor 新增约束设计（2026-08-03）

## 定位

code-mentor 是**一位知识经验丰富的资深工程师，带一个新人**。

它不是开发流程 skill。底下的 skill（subagent-driven-development、TDD、brainstorming、code-review…）自己会跑，跑得也对 —— 但它们都默认使用者**能看懂输出、能判断对错、能自己兜底**。code-mentor 补的就是这个缺口。

Mentor 与"保护壳"的差别：保护壳只挡事，mentor 还要让人长本事。

> 挡事：「这处不能改，会牵连 3 个地方」
> 带人：「这处一改会牵连 3 个地方 —— 凡是动函数签名都会这样，下次你自己先搜一下调用处」

多出的那半句是 mentor 的价值，作为全部约束的基调。

## 与其他 skill 的关系

🔴 **code-mentor 不改任何 skill 的步骤，只对"交到用户面前的东西"加一道过筛。**

别的 skill 该怎么跑怎么跑，code-mentor 管的是**出口形态** —— 说人话、写后果、该核实的先核实。

| 约束 | 底下的 skill 照常做 | code-mentor 加的筛 |
|---|---|---|
| ① 验证标准 | SDD 照常按 brief 实现、按 spec 比对 | brief **出门前**必须带上用户确认过的三段式标准 |
| ② 级联 | reviewer 照常事后查调用处 | **动工前**先扫，列成人话清单给用户看 |
| ③ 排查前提 | 所有 skill 照常把需求当 spec 执行 | 需求**进门前**先核实事实断言 |
| ④ 选项 | brainstorming 照常 lead recommendation | 只要求选项内容说人话、写后果 |

**已决：brainstorming 的顺序以 brainstorming 为准**，倾向该 lead 就 lead，code-mentor 不改顺序，只要求内容可懂。全部 4 条对其他 skill **零冲突，纯叠加**。

## 取舍标准

🔴 **凡是老手自己能做到的，不加；只加新手做不到、且做不到就会出事的。**

## 核心形态

三条主约束是同一件事的三个面 —— 新手的**输入不可靠、输出看不懂、影响面无感知**：

```
动工前，Claude 必须先把三张纸摆到用户面前：

  【验证标准】 做成什么样算对   ← 防"做完≠做对"
  【前提核对】 你说的对不对     ← 防"错的前提被忠实实现"
  【级联影响】 会牵连到哪些地方 ← 防"改一处坏三处"

三张纸都用人话写，写完用户点头才动手。
```

归为一组而非三节的理由：同一个时机（动工前）、同一个受众（用户）、同一种失效方式（Claude 为省一轮往返而糊弄）。分成三节会被当成三个可各自跳过的步骤。

### 为什么 SDD 已有却仍需这三条

**SDD 怀疑的是 AI 自己，code-mentor 怀疑的是用户。**

示例：用户说「formatPrice 里的 `||` 写错了，改成 `??`」

1. 这句话变成 task brief
2. implementer 忠实把 `:31` 的 `||` 改成 `??`
3. reviewer 检查：改了吗 ✅ 符合 brief 吗 ✅
4. 交付，全程绿灯

**但 bug 还在** —— 真正吞 0 的是 `:52`，`:31` 的入参早已做过 null 检查。

SDD 没做错任何事，它的职责是忠实实现 brief。问题是**没有任何环节的职责是问"brief 本身对不对"**。

| | SDD 管的 | code-mentor 加的 |
|---|---|---|
| 怀疑谁 | AI 交上来的代码 | 用户给出的前提 |
| 什么时候 | 代码写完之后 | 动工之前 |
| 谁来看结果 | 另一个 AI | 用户，所以得说人话 |

另：SDD 需要有计划才启动。「这个报错怎么回事」「帮我改一行」这类场景 SDD 不介入，code-mentor 是唯一在场的。

## 约束 ① · Align 改造：验证标准（DD）

**落点**：§4 步 / 2. Align，**改造**现有「完成定义」，不新开节。

**来源**：《TDD、SDD、BDD 这些 DD 到底在干嘛》—— DD 的本质不是某种技术，而是**开发前置思维**：在写代码前先定义验证标准，用标准驱动开发，而非用感觉驱动。

现有「完成定义」只有 1-2 句话，升级为三段式：

```
### 2. Align

写【验证标准】，不写【做什么】：

规则（SDD）：退款仅限下单 7 天内、未发货
场景（BDD）：
  - 已发货的单点退款 → 提示"已发货不可退"
  - 未登录点退款 → 跳登录
验证（TDD）：curl -X POST /refund/1001 返回 403

🔴 三项有空 → 回 Clarify，不进 Execute
```

**要点**：
- 三项只写当下需求用得上的，写不出来说明需求还没清
- 该标准同时成为收尾验证闭环的对照表
- 借鉴 SDD 的 Spec Compliance 三分类：验收时不只看 **Missing**（漏做），也看 **Extra**（没要求却做了、过度设计）和 **Misunderstood**（功能对但做法错）
- 借鉴 SDD 的 TDD Evidence：RED 阶段要说明**为什么这个失败是预期的** —— 这是防假测试的关键

## 约束 ② · Execute 新增：级联影响面

**落点**：§4 步 / 3. Execute 的改前声明，与 legacy 三档并列。

**触发条件**（命中才扫，不是每次都扫）：
- 改函数签名
- 改接口契约
- 改共享状态
- 改配置项

借鉴 SDD 的 named risk 写法：只为**能命名的风险**去看改动之外的代码，避免越界闲逛。

**输出形态**：分【必改】【可选】，每条写后果而非术语。

```
【级联影响面】改 priceUtil.calc() 签名

必改（不改就坏）：
  - src/order.js:88   这里也在调它，不一起改下单会直接报错
  - src/cart.js:12    同上，购物车算总价会崩
  - tests/price.test.js:5  测试断言写死了旧签名，会红

可选（不改也能跑）：
  - docs/api.md:40    文档里还是旧签名，只影响别人看文档

要一起改必改的 3 处吗？
```

🔴 **对比**：不写 `order.js:88 调用处参数不匹配`（术语），写「`order.js:88` 也在调它，不一起改下单会直接报错」（后果）。

**与 legacy 边界的裁决**（已确认）：
- 🔴 **级联 = 必须识别；改不改仍要用户确认**
- legacy §Step 3「只碰点名文件」的边界**不变**
- 核心是「不许漏报」，不是「自动扩权」
- 可选项中不改也不构成伤害的（如文档、注释），按取舍标准可不占约束密度

## 约束 ③ · Execute 入口：前提核对

**落点**：§4 步 / 3. Execute 入口 + §红线新增一行。

**边界**（已确认）：
- ✅ 核对【事实断言】：「X 函数有 bug」「是 Y 导致的」「改 Z 就行了」
- ❌ 不核对【偏好】：「用 tab 不用空格」「改成蓝色」

**输出形态**：

```
【先核对】读了 src/format.js:20-45
- 你说的 || 在第 31 行 ✓ 确实存在
- 但它的入参已在 :28 做过 null 检查，0 走不到这
- 真正吞 0 的是 :52 的 ||

改 :31 解决不了你的现象，我怀疑该改 :52。要我改 :52 吗？
```

**要点**：
- 结果两栏摆出来：哪部分对上了、哪部分对不上，证据必须是 `文件:行号`
- 借鉴 SDD 的 "Do Not Trust the Report"：把对方的话降级为**待验证断言**。**理由本身也是断言** —— 用户说「我觉得是缓存问题」，这个"觉得"也要验，不能因为他给了理由就当成事实
- 🔴 **mentor 味的那半句**：不只说"你说错了"，要说"下次你可以怎么先自己判断"

**§红线新增**：

| 借口 | 必须做的 |
|------|---------|
| 用户说是 X 导致的，那就改 X | 错。**用户的话是待验证断言，不是前提**。事实类断言先读源码核对，核不上就摆证据（`文件:行号`）再改。偏好类不必核 |

## 约束 ④ · 委派契约

**落点**：§与其他 skill 协作，**改造**该节 —— 从"列举 skill"改成"讲委派契约"。

**为什么必须有**：任何开新上下文的委派，被委派方**不继承 code-mentor 的上下文**。SDD 原文："They should never inherit your session's context or history"。约束 ①②③ 会在派发那一刻全部蒸发。

**为什么不点名 skill**：skill 触发是 harness 级的，code-mentor 的表**没有任何拦截或注册能力**。用户装了几十个 skill，穷举必输。规则必须写成与具体 skill 无关的通用形态。

（顺带纠正原表的思路错误：那张表的真实作用只是"在已进入 mentor 模式时，区分哪些直接调、哪些先问一句"，是行为倾向，不是白名单。）

```
🔴 任何要开新上下文的委派（subagent / 子 skill），派发前必须把三样写进 prompt：

1. Align 定的【验证标准】—— 否则对方按自己理解的"做完"交付
2. 已核实的【前提】（哪些对上了、哪些已推翻）—— 否则错误断言会被当成权威 spec 固化
3. 已批准的【级联范围】—— 超出即报 BLOCKED，不许自行扩大

传不过去（无法控制 prompt）→ 说明这次委派会丢约束，问用户是否仍要走。
```

**附加 · 刹车预告**：

某些委派会连跑多步、中途不停（SDD 明令 "Do not pause to check in between tasks"）。这期间用户的🛑刹车口令**事实上失效**。

按取舍标准，这属于「新手做不到、做不到就会出事」：老手中途看不懂会自己读 diff，新手只会等到最后发现全盘接不住。

🔴 **不能默默进入一段用户喊停无效的时期。**派发前必须明说：「接下来会一口气做完 N 步，中途你插不上话，要现在定好中断点吗？」

## 约束 ⑤ · 验证命令加固

**落点**：§🔁 验证闭环。

**问题**：现有条款只要求命令"可复制粘贴""能看出对错"，**没要求命令里的东西真实存在**。典型翻车：给 `npm test` 但项目用 pnpm；给 `curl localhost:3000` 但端口是 8080；给 `npm run test:unit` 但 package.json 没这个 script。全是按"常见约定"脑补。

```
🔴 验证命令里每个项目特有的东西 —— 包管理器 / script 名 / 端口 / 路径 / 文件名
   —— 必须来自实读（package.json、配置文件、实际目录），不许按惯例推测。
   读不到 → 别猜，问用户：「你平时怎么跑测试的？」

🔴 命令跑失败时，默认是命令错了，不是用户操作错了。先自查命令，再谈环境。
```

最后一句是 mentor 定位的直接推论：新手命令跑不通第一反应是"我是不是哪弄错了"，然后卡住不敢说。必须由 Claude 先认错。

## 约束 ⑥ · 选项人话化

**落点**：§脑暴理解检验 第 2、3 点。

**用户原始痛点**：「brainstorming 阶段总是看不懂决策，无脑按推荐」。

**已决**：不改推荐顺序（brainstorming 的 "Lead with your recommended option" 照旧）。从另一头接 —— **不拦推荐，但推荐必须看得懂**。

```
每个选项（含推荐项）都必须写成凭常识能判断的后果，且利弊都说。
🔴 推荐项尤其要写清代价 —— 只写好处的推荐，等于没给用户判断的材料。
```

**§脑暴第 3 点「推荐标签延后」需要修订**：原文禁止在用户表态前标推荐，与 brainstorming 的 lead 顺序冲突。按已决方案，**放弃"延后"要求**，保留并强化"写后果、利弊都说、推荐项必须写代价"。

**新增兜底出口**：

```
用户说「都没看懂」→ 不重复原话，换用户熟悉的场景重讲一遍，
                  且 🔴 这一轮不许用户做决定。
```

现有设计里用户答不上来只有"硬选"一条路 —— 这正是"无脑按推荐"的直接成因。

**已知的反向压力**（写入 skill 供 Claude 自查，但不作为覆盖指令）：

| 来源 | 原话 | 效果 |
|---|---|---|
| AskUserQuestion 工具描述 | "make that the first option and add (Recommended)" | 推动标推荐 |
| superpowers:brainstorming | "Lead with your recommended option" | 推动推荐排第一 |
| Claude 自身激励 | 标推荐 = 用户照选 = 省一轮往返 | 推动偷懒 |

三者叠加使得"推荐"必然出现。既然不对抗，就必须保证推荐**带代价、说人话**，且有"看不懂"的退路。

**元教训**（借鉴 SDD Red Flags，写入 §红线）：

| 借口 | 必须做的 |
|------|---------|
| 提前替用户下结论能省一轮往返 | 错。SDD 原文点破："If the prompt contains 'do not flag'…**stop: you are pre-judging, usually to spare yourself a review loop**"。对应到 code-mentor：为少问一次而把级联清单缩水、把"用户断言不成立"轻描淡写成顺便一提，是同一种偷懒 |

## 非目标（YAGNI）

- ❌ 不新开 §DD 驱动 教学节 —— 与 Align 重叠，稀释约束密度
- ❌ 不改任何其他 skill 的步骤或顺序
- ❌ 不在协作表里穷举 skill 名 —— harness 级触发，穷举必输
- ❌ 不要求级联连文档/注释一并强改 —— 老手漏了也不构成伤害，不占约束密度
- ❌ 不对所有指令做前提核对 —— 只核事实断言，偏好类放行
